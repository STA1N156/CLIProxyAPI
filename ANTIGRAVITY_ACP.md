# Antigravity through the official CLI

Antigravity generation now runs through the official `agy acp` process. CPA keeps its OpenAI, Claude and Gemini HTTP interfaces; the official CLI creates the Google requests, TLS connections, request identifiers, labels and auxiliary calls.

The transport follows the IDE MCP bridge used by [Magpie's agy-cli plugin](https://github.com/magpie-community/plugins/tree/main/packages/agy-cli). A private `nc` executable is visible only to CPA's child processes. Client tools are exposed with `antigravity/alwaysLoad`, and results continue the pending ACP turn. Permission requests are accepted only for declared client tools. CLI filesystem, terminal and browser permission requests are rejected.

## Configuration

```yaml
antigravity:
  acp:
    enabled: true
    path: agy
    max-processes: 128
    max-sessions: 32
    max-queue: 4096
```

ACP is enabled by default. Docker includes official CLI 1.5.9 for Linux amd64/arm64 and verifies its download checksum. For a native CPA installation, install `agy` on PATH, set `AGY_PATH`, or configure `path` with the executable's absolute path. Set `enabled: false` to use the previous direct HTTP implementation.

State defaults to `<auth-dir>/.acp`; persist it together with the credentials directory. Processes are grouped by credential, proxy and the complete tool schema. Each group uses isolated profiles and workspaces; each conversation has its own ACP session. Different tool definitions or accounts never share a process. The profile contains official credentials and conversation data and must be treated as private. Model catalogs are cached per credential for three hours.

The official default system prompt remains enabled. Client system instructions are prepended to the first user input. `requestType`, generation limits and internal labels are generated by the official CLI. CPA does not rewrite Google's requests.

## Concurrency and memory

Each official process serves up to 32 resident ACP sessions. The default global cap is 128 processes, allowing up to 4096 resident sessions when requests share compatible account/tool groups. The waiting queue holds up to 4096 additional requests; excess requests receive HTTP 503. Account or tool-schema fragmentation can leave some process slots underused. Google account quotas and server resources still determine sustainable throughput.

The bridge preserves Magpie's IDE MCP transport and adds routing by the official `antigravity.google/conversation_id` metadata. Every tool call must name a live session belonging to that process, and the tool must exist in that session's catalog. Missing or unknown conversation identifiers return an error. Permission decisions also use the ACP session ID. The bridge never guesses which active conversation owns a call.

Completed sessions are reused, or evicted under pressure and restored with `session/resume`. Session metadata records the owning worker so restoration uses the same official profile. If a session moves to a different worker, CPA replays its history. Idle sessions and workers are reclaimed after ten minutes. Under pressure, an abandoned tool wait can be reclaimed after 30 seconds. Cancellation closes only the affected session, keeping sibling sessions running. Process exit terminates its child helpers.

The previous design needed one process per conversation. A local Windows run now served 32 concurrent tool conversations in one official process, with roughly 255 MiB RSS at the sampling point. This is a local mock-service measurement, not a 3000-request production benchmark. Set `max-processes` to fit the available RAM and CPU; multiple instances need conversation affinity at the load balancer.

## Behavior and boundaries

| Area | Previous direct HTTP path | ACP path |
|---|---|---|
| Google requests | Assembled by CPA | Generated by official CLI |
| System instructions | CPA's request transformations | Official prompt plus client instructions in first input |
| Context | HTTP history translated each request | Resident official conversation, resume after eviction |
| Tools | Translated Google function calls | Client tools through IDE MCP, continuing the same turn |
| Thinking | Google response parts | Official ACP thought chunks converted to the client format |
| Model list | CPA registry and capability hints | Models offered by the account's ACP session |
| Token counting endpoint | Google countTokens request | Local O200k estimate, without an extra Google request |
| Resource cost | HTTP connection pools | Bounded official processes plus request queue |

Inline images are supported. Audio, video and file URLs receive a clear HTTP 400 because this ACP bridge does not expose them. External `temperature`, `max_tokens`, tool-choice constraints and equivalent sampling overrides are not forwarded; generation settings follow the official CLI. Generic management HTTP calls retain CPA's existing implementation. This is not a raw pass-through of every CPA management API into ACP.

Validation used the actual official Windows CLI against a local mock Google service: model discovery, multi-turn context, thinking, consecutive tool results, 32 simultaneous tool conversations sharing one official process, correct tool arguments and results for each conversation, and one cancelled session while a sibling completed successfully. No production account quota was used. Docker's Linux image has not been built in this workspace.
